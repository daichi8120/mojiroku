# 0016. カレンダー取り込み（限定公開 iCal URL = 秘密 URL を貼るだけ・読み取り専用）

- ステータス: 採用（**取得方式は [[ADR-0019_連携のOAuthワンクリック化]] で Google OAuth + Calendar API `events.list` に移行**。OAuth 未連携時は本 iCal 経路へフォールバックするため引き続き有効。本 ADR が「重い別プロジェクト」として却下した OAuth Desktop を、loopback で $0 のまま実現できると分かったため再評価して採用した）
- 日付: 2026-06-27

## Context

Phase 6（連携）の最後のスライス。Notion AI ミーティングノートや Fireflies/tl;dv のように、**予定からタイトルを
自動入力して録音を始める**取り込み体験を作る（Phase 5 のモック `IntegrationsView` が示す UX：接続 → 次の予定 →
「記録を準備」）。固有の難所は **Google カレンダー API が OAuth 前提**で、北極星の **$0・OAuth 不要・審査不要**
（[[ADR-0013_Notion書き出し]] / [[ADR-0014_Slack送信]] が同じ理由で OAuth を回避済み）と
正面衝突する点。

論点と選択肢:

1. **方向**: (取り込み) 予定 → 録音タイトル自動入力 vs (書き出し) 議事録 → カレンダー予定。
   → ユーザー確認の結果 **取り込み**（製品価値が高くモックに一致）。
2. **認証/取得**: (A) **限定公開 iCal URL**（秘密アドレスを GET・読み取り専用）、(B) OAuth 2.0 Desktop（PKCE+
   ループバック・双方向）、(C) サービスアカウント JSON。
3. **繰り返し予定の扱い**: Google の `basic.ics` は繰り返しを**展開せず単一 VEVENT + RRULE で返す**ため、
   「週次定例」を「次の予定」に出すには RRULE 展開が要る。

裏取り済み（[[verify-load-bearing-assumptions]]）:
- **限定公開 iCal URL は実在する**。`設定 → カレンダーを統合 → iCal 形式の限定公開 URL`＝
  `https://calendar.google.com/calendar/ical/<id>/private-<token>/basic.ics`。推測不能な秘密 URL を **OAuth/API キー
  なしの HTTPS GET** で取得できる（＝Slack Incoming Webhook と同型の「秘密 URL を貼るだけ」）。Workspace 管理者が
  無効化していると欠落・ユーザーは「リセット」で失効可能。
- **RRULE は展開されない**（master VEVENT に RRULE、例外は EXDATE・差し替えは RECURRENCE-ID）。
- **キャッシュ遅延**: 「12〜24h」は *Google が外部 ICS を購読する側*の話で別物。こちらが Google 自身の basic.ics を
  直接 GET する場合でもエッジキャッシュで直近変更の反映に多少のラグがあり得る → UI で開示する。

設計判断（**ハンドロール**。アドバイザー確認済み）:
- **クレートは難所を肩代わりしない**。RRULE の意味論はイベントの**ローカル壁時計**で定義される（「毎週火 15:00」は
  DST に関係なく 15:00）。よって展開は `NaiveDateTime` 加算が最も単純かつ DST ドリフトを生まない。`rrule`+`chrono-tz`
  は MVP がスキップする TZID→絶対時刻変換にしか効かず、むしろ総工数が増える。`notion.rs`/`slack.rs` と同規模の
  ハンドロールが正解。

## Decision

**限定公開 iCal URL（方式 A）＋ ハンドロール iCal パーサ＋ DAILY/WEEKLY の壁時計展開**で実装する。
OAuth・サーバ・新規重量依存ナシ・$0・読み取り専用・審査不要。

- **コア `crates/mojiroku-core/src/calendar/mod.rs`**（UI 非依存・テスト可能）:
  - `CalendarFeed { ical_url }.fetch_upcoming(now, window_days, max)` → `Vec<CalendarEvent>`（id/title/start/end?/location?）。
  - ureq GET（タイムアウト・本文サイズ上限・`BEGIN:VCALENDAR` 検証）。**URL 検証は
    `https://calendar.google.com/calendar/ical/` プレフィックス固定**（誤 URL で秘密を他ホストへ送らない）。
  - 行アンフォールド（RFC5545）/ `SUMMARY`・`LOCATION` のアンエスケープ（`\,` `\;` `\n` `\\`）/
    `DTSTART`・`DTEND`・`RRULE`・`EXDATE`・`RECURRENCE-ID`・`UID` を抽出。
  - **時刻正規化**: `...Z`(UTC) は呼び出し側が注入する `now` のオフセットで**ローカル壁時計へ変換**（テスト決定的・
    `clock` 不要）。TZID/浮動は壁時計をそのままローカル扱い。**全日（VALUE=DATE）は一覧から除外**。
  - **RRULE 展開**: DAILY / WEEKLY（+INTERVAL/BYDAY/COUNT/UNTIL/EXDATE）を窓内で壁時計展開。RECURRENCE-ID は
    マスタの当該発生を除外（override が差し替え時刻で 1 件出す＝重複排除）。
  - 進行中・未来かつ窓内のみ、開始昇順、件数上限。
- **Tauri `src-tauri/src/lib.rs`**:
  - `CALENDAR_ICAL_KEY = "calendar_ical_url"`（**キーチェーン**。URL は秘密なので `secrets` の has/set/delete のみ公開し
    **JS へ読み戻さない**。エラーにも URL/トークンを含めない＝[[ADR-0014_Slack送信]] の漏洩防止を一般化）。
  - `list_calendar_events()`（spawn_blocking・`now = Local::now().fixed_offset()` を core へ注入）。
  - `stop_mic_recording(diarize, title?)` に `title` を追加（「記録を準備」由来の予定タイトルで保存。無ければ既定「録音」）。
- **フロント**:
  - `IntegrationsView` カレンダー節を**実配線**（URL 貼付→接続/切断・次の予定=実フィード・「記録を準備」→
    `startMicRecording()` + `navigate(recording, title)`）。**会議プラットフォーム/書き出し先は引き続きモック**で `PreviewTag`
    を各節に明示（[[mojiroku-ui-redesign-dark-studio]]）。
  - 接続状態は `hasSecret` のみで表示（**URL/メールは出さない**）。キャッシュ遅延を UI で開示。

## Consequences / リスク

- ⚠️ **実データ検証が load-bearing**（CLAUDE.md「実データで確認」）: 自分の限定公開 URL を貼り、**週次定例を含む
  実予定が正しいローカル時刻で出る**ことを確認する。fixture ユニットテスト（weekly/all-day/Z 時刻/EXDATE/折返し/
  RECURRENCE-ID）でバック。
- **読み取り専用・取り込みは画面表示時の GET だけ**（自動同期なし。roadmap「外向きは操作時のみ」に一致）。
- **却下した代替**:
  - (B) OAuth Desktop = 機微スコープの **Google アプリ審査**＋未署名「壊れている」警告に**もう一段の警告画面**が重なる。
    ADR-0013/0014 の $0・審査不要方針から外れる重い別プロジェクト（双方向が必要になったら再検討）。
  - (C) サービスアカウント JSON = 強力な鍵をユーザーが管理＋カレンダー共有が必要で非技術者には不向き。
- **MVP の制限（UI/コードで開示）**:
  - 対応 FREQ は **DAILY / WEEKLY のみ**。MONTHLY/YEARLY はマスタ 1 回（窓内になければ出ない）。
  - **TZID は壁時計をローカル扱い**（同一 TZ で正しい・異 TZ の予定は時刻がずれ得る）。
  - 全日予定は一覧から除外。Google 側キャッシュで直近変更の反映にラグあり（「更新」で再取得）。

## 追記（2026-08-30）— 却下理由の 1 つが現実になった

本 ADR が OAuth Desktop を却下した理由にこれがあった。

> (B) OAuth Desktop = 機微スコープの **Google アプリ審査**＋未署名「壊れている」警告に**もう一段の警告画面**が重なる。

[[ADR-0019_連携のOAuthワンクリック化]] はこれを**認識したうえで**移行を決めている
（「Calendar は sensitive scope → 未確認アプリ警告 + 100 ユーザー上限（ベータ <100 人で警告許容の方針）」
「未確認 → 警告許容・ベータ <100 人・将来 verify」）。署名の導入
（[[ADR-0022_AppleDeveloperID署名とnotarization]]）で「未署名の警告」は消えたが、
**もう一段の警告**のほうは想定どおり残り、Issue #42 として表面化した。
つまり見落としではなく、**先送りしていた判断の期限が近づいた**という話。

分かったこと（2026-08-30 時点）。

- 審査は 2 段ある。**ブランディング審査**（同意画面に名前とロゴを出す）は 2026-08-30 に完了
- **機微スコープ審査**（警告画面の除去）は未提出。デモ動画が要る
- 未審査のあいだ **100 人の生涯上限**がかかる。同時ではなく累計で、**リセットできない**

**iCal 経路を残した判断は正しかった。** 審査に依存しない道が確保されている。
ただし現状 UI から iCal URL を**入力する経路が無い**。`CALENDAR_ICAL_KEY` に対して
フロントが呼ぶのは存在確認（`hasSecret`）と削除（`deleteSecret`）だけで、保存する
呼び出しが無い（`frontend/src/features/integrations/IntegrationsView.tsx`）。
審査が長引く場合は、その入口を戻すことが選択肢になる。
