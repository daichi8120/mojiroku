# ADR-0030: 要約モデルを端末のメモリで段分けする

- 状態: 採用（骨組みのみ。**配るモデルはまだ変えていない**）
- 日付: 2026-08-30
- 関連: [ADR-0021](./ADR-0021_FFI例外シールドと重処理の直列化.md)（16GB 機のメモリ枯渇）、[ADR-0007](./ADR-0007_要約llamaを別バイナリsidecarに分離.md)（sidecar 分離）、[ADR-0029](./ADR-0029_プロンプトはモデル自身のchatテンプレートで組む.md)（系統を跨ぐ前提）、Issue #30、Issue #4（横断評価）

## Context

いま全員が同じ 1 本を落とす。`Qwen2.5-7B-Instruct-Q4_K_M.gguf`、約 4.4GB。16GB のマシンにも 64GB のマシンにも同じものが降りる。

**非力な端末には重すぎる。** 要約 sidecar はモデル全体をメモリに載せる。16GB 機ではメモリ枯渇でクラッシュした前例があり、重い ML ジョブをアプリ全体 1 本に直列化したのはその対策だった（ADR-0021）。直列化は「同時に載せない」ための策で、「載せるもの自体を小さくする」策ではない。

**余裕のある端末には物足りない。** もっと大きいモデルを載せられるのに使っていない。

差し替えの前提は 2 つとも揃った。

- 系統を跨げる（ADR-0029。GGUF に焼かれた chat テンプレートを使う）
- Qwen3 系の思考出力を切れる（`--no-think`、Issue #29）

### 候補は測ってある。境界は測っていない

11 モデル × 4 タスク = 154 生成の横断評価を済ませた（Issue #4）。段に置く候補はそこから決まる。

| 段 | 候補 | サイズ | 平均秒 | 機械採点 | 議事録の見出し |
|---|---|---|---|---|---|
| 小 | Qwen3.5-4B | 2.7GB | 10.7 | 2/14 | 2/3 |
| 中（現行） | Qwen2.5-7B | 4.7GB | 18.8 | 0/14 | 3/3 |
| 中（候補） | Qwen3.5-9B | 5.7GB | 17.5 | 0/14 | 3/3 |

**測っていないのは「何 GB の端末で何を選ぶか」。** 生成の質と速度は測ったが、whisper・話者分離と同居したときのメモリ挙動は見ていない。「載る」ことと「快適に動く」ことは別で、境界はそこで決まる。

## Decision

**構造だけ先に入れ、値は後から入れる。** 段の仕組みを実装し、配るモデルは現行のまま据え置く。

### 1. モデルはカタログに 1 行 1 モデルで持つ

`crates/mojiroku-core/src/models/mod.rs` の `SUMMARY_MODELS`。1 行が DL 元・期待ハッシュ・サイズ・段・ライセンス・採用可否を持つ。

以前は既定モデル名・base URL・期待ハッシュが別々の定数に散っていた。段ごとにモデルを持つとその 3 つがモデル数だけ増え、対応が崩れる。**崩れてもビルドは通る**ので、気づくのは利用者の DL が `checksum_mismatch` で落ちたときになる。

### 2. 採用済みが無い段は既定へ落ちる

`adopted: false` のモデルは決して選ばれない。品質ゲートを取り直していないモデルを、段が決まったというだけで配らないため。

いま `adopted` は現行の 1 件だけなので、**どの段でも既定が返る＝現行の挙動と同じ**。差し替えはこのフラグ 1 つで行う。

### 3. 見るのは搭載メモリ。空きメモリは見ない

空きメモリは起動のたびに変わる。同じ端末が、ブラウザを開いているかどうかで違う段に落ちる。落とし直しが数 GB のダウンロードである以上、判定は端末ごとに安定していないと使えない。

空きメモリを見るなら、それは「いま実行してよいか」の判断（ADR-0021 の直列化）であって、「何を落とすか」の判断ではない。

macOS の `sysctl hw.memsize` を読む（`crates/mojiroku-core/src/hardware.rs`）。必要なのはこの 1 つの数値だけなので `sysinfo` は足さない。

### 4. 分からないときは小さい方へ倒す

取得できない場合（macOS 以外、取得失敗）は小の段にする。外したときの損害が非対称だから。

- 大きすぎるモデル → メモリ枯渇でクラッシュしうる（ADR-0021 の実績がある）
- 小さすぎるモデル → 要約の質が落ちるだけ。設定から上げ直せる

### 5. 手元にあるモデルを黙って置き換えない

`select_summary_model` は段の判定より先にキャッシュを見る。既に落としてあるモデルがあれば、段が別のものを指していてもそれを返す。

数 GB の再ダウンロードは、利用者にとって「勝手に始まった」以外の何物でもない。乗り換えは設定から明示的に行う（UI は次の増分）。

**規約ではなく構造で守る。** テストが分岐を固定している。

## 検証

- **挙動が変わっていないことを機械的に固定した。** 既定モデルの DL URL と期待ハッシュは 1 バイトも変えていない。テストは refactor 前の値を直接書いて比べる（カタログから引いて比べると、両方ずれても通ってしまう）
- 現行モデルの SHA-256 を HF の paths-info API で取り直し、ソースの既存値と一致することを確認した（手順そのものの裏取り）
- 候補 2 本は**未認証**で 302（gated でない）・`apache-2.0`・`gated: false` を HF API で確認済み。リビジョンを固定し、SHA-256 は LFS の `oid` から取った
- **テストに変異を入れて、落ちることを確かめた**（4/4 検出）

| 変異 | 検出したテスト |
|---|---|
| 候補を `adopted: true` にする | `every_tier_still_resolves_to_the_current_default` |
| キャッシュ優先の分岐を消す | `multiple_cached_models_resolve_deterministically` |
| 未取得時を Large に倒す | `unknown_memory_falls_to_the_small_tier` |
| 既定モデルのハッシュを 1 文字変える | `summary_registry_preserves_the_current_download` |
| 段の境界を逆転させる | コンパイル時（`const _: () = assert!`） |

⚠️ `cached_model_wins_over_the_tier_choice` は**名前に反してキャッシュ優先の分岐を踏んでいない**。手元が 1 件だけだと、その分岐を消しても後段が同じ答えを返すため。実際に変異が素通りすることを確かめ、コメントに残した。

## 影響・制約

- **利用者に届くモデルは変わらない。** 段の選択は実装されたが `transcription.rs` はまだ `DEFAULT_SUMMARY_MODEL` を直接使う。配線は次の増分
- 候補は DL されないので `NOTICE` は据え置く。**採用時に追記する**
- 段の境界（16GB / 32GB）は Issue #30 のたたき台のまま。**実測で決め直す**前提で、テストは値を固定していない（順序だけ固定）
- 差し替えるときは**要約の品質ゲートを取り直す**。実会議での評価が PASS 済みなのは現行モデルについてであって、段の仕組みについてではない
- プロンプトの英語 instruction は Qwen2.5 に合わせて実測で詰めた文面。モデルを替えるなら詰め直しが要る

## 対象外

- 文字起こし（whisper）モデルの段分け。まず要約モデルだけ
- クラウド（BYOK）経路。スペックに関係しない
- 実行中の動的な切り替え。起動時に決めるだけ
- **用途ごとに別モデルを持つか**は決めていない。横断評価では Phi-4-mini が議事録の 4 見出しを一度も揃えられず（0/3）、タイトルや要約は通った。**段を下げるとまず議事録の形式遵守が落ちる**という形で、用途差は実在する。段を「モデル 1 本」にするか「用途ごと」にするかは Issue #30 で継続
