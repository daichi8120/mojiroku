# 0026. 会議開始の自動録音プロンプト（カレンダー時刻トリガー＋メニューバー常駐＋通知→アプリ内確認）

- ステータス: 採用（増分1 実装完了。実カレンダー予定でのエンドツーエンド E2E を 2026-07-18 に確認済み）
- 日付: 2026-07-18
- 関連: [[ADR-0016_カレンダー取り込み]]（予定データの取得元＝iCal / Calendar API）/ [[ADR-0019_連携のOAuthワンクリック化]]（Google OAuth トークン）/ [[ADR-0024_バックグラウンドジョブ基盤]]（tokio 常駐タスクの前例）/ [[ADR-0022_AppleDeveloperID署名とnotarization]]（署名 .app での TCC 永続）/ [[ADR-0017_会議モードのシステム音声キャプチャ]]（増分2 のアプリ/音声検知が接続する先）

## Context

競合（Granola / Fireflies / Notion AI ミーティングノート）は、**会議が始まると自動で「録音（ノート取得）しますか？」と促す**。mojiroku は録音開始が完全に手動で、「会議が始まってから録り忘れに気づく」取りこぼしが起きる。**Notion を参考に、会議開始時に自動で録音開始を促す通知**を出したい。

既にある土台: カレンダー連携（[[ADR-0016_カレンダー取り込み]] / [[ADR-0019_連携のOAuthワンクリック化]]）で予定（タイトル・開始/終了時刻・場所）を取得でき、連携画面には手動の「記録を準備」（録音開始＋タイトル付与＋話者分離 ON）がある。欠けているのは **①開始時刻を監視して発火する常駐 ②OS 通知 ③通知から録音への導線**。

「会議が始まった」の検知には 2 系統がある:
- **カレンダー開始時刻ベース**（手持ちデータで作れる。予定された会議をカバー）。
- **会議アプリ/音声検知**（Zoom/Teams デスクトップのプロセス走査、システム音声の発生）。カレンダーに無い突発会議を拾えるが重く、穴がある。

## Decision

**縦の薄い一本（増分1）を先に出す**: **カレンダー予定の開始時刻**をトリガに、**メニューバー常駐**で監視し、**OS 通知**を出し、**クリック→アプリ内「録音?」プロンプト**（既存「記録を準備」フロー流用）で録音を始める。会議アプリ/音声検知は**増分2（次リリース）**に回す。

北極星との整合: **通知は"きっかけ"を出すだけで、録音は必ずユーザーのクリック**（自動録音しない＝「送信・記録はあなたの操作だけ」）。検知は**プロセス走査を優先し音声の常時監視は避ける**（増分2 の設計制約）。

### 1. トリガー = カレンダー開始時刻（増分1）

Rust 側の tokio 常駐タスクがカレンダー予定を定期取得（既存の iCal / Calendar API 経路を再利用）し、各予定の**開始時刻**（＋任意で N 分前）に通知を発火する。dedup として**通知済みイベント ID を記録**し二重発火を防ぐ。カレンダー未接続時は無効（通知しない）。全日予定は対象外（既存 API が除外済み）。

### 2. メニューバー常駐（Phase 11 を一部前倒し）

会議開始時に mojiroku が起動していないと通知は出せない。よって **`tray-icon` でメニューバーに常駐**させ、ウィンドウを閉じてもプロセスは生かす（スケジューラを回し続ける）。トレイメニューは「表示 / 終了」（＋設定トグルは §5）。ライト版のグローバルショートカット録音（Phase 11 の残り）は本 ADR の対象外。

### 3. 通知 → アプリ内「録音?」プロンプト（macOS 制約への確定形）

**`tauri-plugin-notification` は macOS でアクションボタン付き通知を非対応**（Actions API はモバイル専用。一次情報で確認）。よって「通知に『録音開始』ボタン」は取れない。確定形は:

1. プレーン通知「『◯◯会議』が始まりました — 録音しますか？」
2. 通知クリック → macOS がアプリを activate → **アプリ内で「この会議を録音?」プロンプト**（既存 `prepare`＝`startMicRecording` + タイトル付与 + 話者分離 ON を流用）。

クリックとイベントの対応付けはクリックコールバックに依存しない: **スケジューラが「直近に始まった会議」の状態を保持**し、フロントへイベントで渡す。ウィンドウを開いた/前面化した時にその状態があればプロンプトを出す。バナーを見落としても（下記の抑制時も）アプリを開けばプロンプトが受け皿になる（二重の受け皿）。

### 4. macOS 通知の実機挙動（2026-07-18 裏取り済み）

- **`.app` バンドルでは `com.daichi0812.mojiroku` 帰属**で通知許可・発火する（許可プロンプトも「mojiroku」名義）。**実装・配布はこれで成立**。
- **`just dev` は Terminal 帰属**になる（アプリを Terminal の子プロセスとして起動するため）。通知の実機確認は**ビルドした .app で行う**（[[ADR-0017_会議モードのシステム音声キャプチャ]] が ad-hoc .app で先行検証したのと同じ段取り）。
- **出したアプリ自身がアクティブだとバナーは抑制**され通知センター直行（macOS 仕様）。実際の会議開始時はユーザーが Zoom/ブラウザにいて mojiroku は非アクティブ＝**バナーが出る**。アクティブだった場合も §3 のアプリ内プロンプトが受け皿。
- **TCC 許可が更新（新 cdhash）を跨いで永続するか**は署名 .app（[[ADR-0022_AppleDeveloperID署名とnotarization]]）で別途確認（増分1 リリース時）。ローカル無署名でも通知自体は出る。

### 5. 設定（増分1）

`settings.json` に `auto_record_prompt`（ON/OFF・既定 OFF で明示オプトイン）を追加。将来の拡張余地としてタイミング（開始時 / N 分前）・対象（全予定 / 会議リンク有）を持てる形にするが、増分1 は最小（開始時・全タイム予定）で出す。

## 検証

- 通知＋トレイの実機裏取り（2026-07-18）: §4 のとおり完了（トレイ常駐・mojiroku 名義通知・発火）。実装は `src-tauri/src/tray.rs`。
- **常駐（2026-07-18 実機）**: ウィンドウを×で閉じてもプロセスは生存し、トレイ「表示」／Dock 再クリックで再表示される（`WindowEvent::CloseRequested`→prevent_close+hide／`RunEvent::Reopen`）。Cmd+Q は従来どおり完全終了。
- **エンドツーエンド E2E（2026-07-18 実機・.app・実 Google カレンダー）**: 予定開始 → OS 通知（mojiroku 名義）＋アプリ内「録音?」プロンプト（予定タイトル付き）→「録音する」→ 話者分離 ON で録音開始 → 停止で予定タイトル「テスト会議」として保存、まで通しで成立。
- `started_within`（開始済み かつ 猶予内）を単体テスト（境界含む）。dedup は通知済み ID 集合＋猶予窓。
- ビルド/テスト: `cargo build/clippy/test --workspace`・`npm run build`（tsc+vite）緑。

## 影響・制約

- **常時オン前提**: 通知が要る間は mojiroku（＋常駐スケジューラ）が起動している必要がある。スリープ中や終了中は発火しない。
- **増分2 の穴（先出しで明記）**: 会議アプリ/音声検知は、**ブラウザの Google Meet がプロセス走査で見えない**（Chrome のタブ）・システム音声の常時センシングは重く北極星と擦れる。増分2 で扱うが「両方」は完全網羅を約束しない。
- **アクションボタン非対応**は macOS プラットフォーム制約であり将来の Tauri 更新でも自動では変わらない（§3 の in-app 確認が恒久的な確定形）。

## 追記: 会議モードにも予定タイトルを渡す（2026-08-25）

§3 のプロンプトから始まるのはマイク録音だけで、**会議モード（システム音声）はカレンダーの予定名を受け取っていなかった**。会議モードの録音は必ず既定の「会議」になっていた。

予定名は録音を識別する情報の唯一の供給源で、文字起こしからは復元できない（会議では相手の名前や社名を口に出さないため。Issue #4 で実データ 19 本を測って確認）。そこで会議モードの開始時にも解決するようにした。

**判定は「保留状態の寿命を管理する」のではなく、「録音を始めるこの瞬間に使ってよいか」を 1 回だけ行う。**

- `resolve_meeting_title` コマンドが、保留中の予定が**まだ進行中**（`still_running`）なら題名を返す
- 終了時刻があればそれまで、無ければ開始から 60 分（`ASSUMED_MEETING_MIN`）を仮定する
- 発火の猶予（`START_GRACE_MIN` = 5 分）とは窓が別。あちらは「通知を出すか」、こちらは「題名を付けてよいか」。通知に気づいて 6 分後に録音を始めた人が題名を貰えない、という退行を避けるため長い
- **フロントに時刻計算を書かない。**二重定義になっていずれズレる。TS 側はコマンドを呼んで結果を使うだけ

プロンプトは従来どおりユーザーが操作するまで残る（自動失効させない）。放置された予定の題名が無関係な録音に付く問題は、上の「使う瞬間に判定する」形で塞いでいる。
