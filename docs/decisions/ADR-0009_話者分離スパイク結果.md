# 0009. 話者分離スパイク結果 — sherpa-onnx で go（Phase 2b で consolidation 前提）

## Context

ADR-0004 で話者分離は **sherpa-onnx**（pyannote seg-3.0 の ONNX 重み + 話者埋め込み + **しきい値クラスタリング**、torch なし）と決めたが、
ADR-0004 自身が「埋め込み/クラスタリングが pyannote.audio と異なる → 品質は同一保証ではない → **早期スパイクで検証**」と明記していた。
さらに反証の兆候（sherpa-onnx issue #1708: PyTorch pyannote と乖離しほぼ単一話者に潰れる報告）があった。
北極星でも品質ゲートが最重要。よって**フル統合の前に「品質 go/no-go スパイク」**を実施した。

スコープは判定のみ。実施は scratchpad に隔離（Python・Rust 不要）、本体リポジトリは未変更（本 ADR のみ）。

## 検証方法

- 環境: `pip install sherpa-onnx`（1.13.3、bundled onnxruntime、**ort 非依存**）を Apple Silicon に。
- 音声: 実日本語会議 1 本の抜粋（3:00–13:00、実質 3 話者 A/B/C ＋ ほぼ無音の 4 人目）。
  **正解ラベルはユーザー提供の「大雑把」な手動区間**（厳密 DER ではない。purity 数値は ± 軟らかい）。
- 指標: 100ms フレームで GT 話者 × 予測クラスタの分布を取り、各 GT 話者の主クラスタ purity・被覆・leak 先を観測。
- モデルを総当たり: segmentation ×2（pyannote-seg-3.0 / reverb-diarization-v1）、embedding ×3（TitaNet-large en / 3D-Speaker eres2netv2 zh / eres2net en-voxceleb）、クラスタリング（fixed N vs threshold スイープ）。

## 観測（実音声）

- ✅ **Apple Silicon で動く**: wheel + 全 ONNX モデルがロード/実行。**#1708 の単一話者潰れは再現せず**（zh ベースラインも TitaNet も均衡したクラスタを出す）。
- ✅ **速度**: reverb-seg + TitaNet で **0.41×RT**（CPU/Python）。53 分会議 ≈ 22 分。Rust/CoreML で改善余地。実用圏（オフライン）。
- ⚠️ **被覆は segmentation モデルで決まる（埋め込みではない）**: pyannote-seg-3.0 → **被覆 62–78%**（大量取りこぼし）。**reverb-diarization-v1 → 被覆 98–99%**。← 最大の発見。
- ✅ **日本語の声は分離する**: reverb-seg + TitaNet + **threshold モード**（num_clusters=-1）で th 0.75–0.90 のどれでも **A/B/C が別クラスタに割れる**。
  - th=0.80: purity **A=75% / B=72% / C=97%**、被覆 98–99%。
- ⚠️ **fixed N は潰れる**: num_clusters=3 を強制すると 531/47/13 と 1 クラスタへ収束（FastClustering の agglomerative-to-k が衛星クラスタを優勢塊へ併合する癖）。
  → **「人数既知なら固定」という近道は使えない。threshold モード必須。**
- ⚠️ **過分割が残る**: 3 話者に対し th 0.75→0.90 で 13→8 クラスタ。**threshold 調整だけでは 3 に到達しない**（尾の小クラスタが残る）。

### 決め手: leak 先の正体（th=0.80）

非優勢時間が「回収可能な尾」か「相手話者への真の混同」かを分けて判定した:

| GT | 主クラスタ purity | 尾クラスタへ(回収可) | 相手優勢へ(真の混同) |
|----|------|------|------|
| A (102s) | 75% | spk00=19s に **19%** | B へ 5% |
| B (365s) | 72% | spk17/13 等に **~16%** | A へ **10%** |
| C (92s)  | 97% | — | — |

→ **非優勢分の大半は回収可能な尾クラスタ**で、相互混同は少数（A↔B ~5–10%）。
consolidation（尾を最近接の主クラスタへ畳む）で purity は引き上がるはず。残る **A↔B ~10% が真の下限**。→ 下記で実機確認した。

### consolidation スパイク結果（残る load-bearing 不明点の検証・実機）

「過分割を後処理で ~3 話者へ畳めるか」を Python で検証した。各 turn から TitaNet 埋め込みを取り、2 戦略を比較:

| 手法 | クラスタ数 | A purity | B purity | C purity | 分離 | oracle整合 |
|------|------|------|------|------|------|------|
| baseline（無処理） | 11 | 75% | 72% | 97% | ○ | 77% |
| **A: anchor+再割当（尺≥30s を anchor、全 turn を最近接 centroid へ）** | **3** | **94%** | **79%** | **97%** | **○** | **84%** |
| B: centroid 凝集（K=3 まで cosine 併合） | 3 | 99% | 85% | 98% | **×混同** | 90% |

- ✅ **戦略 A が決定打**: 人数を教えずに**ちょうど 3 クラスタ**へ収束し、**A/B/C の分離を維持**（○）、purity を **A 75→94%**（leak 分析どおり A の 19% 尾が正しく A へ畳まれた）/ B 72→79% / C 97% へ改善。
- ⚠️ 戦略 B は purity 数値は高いが**分離×（A/B が融合）** = fixed=3 と同じ「全部一塊で偽高 purity」。**尺で anchor を固定する方式が頑健**（尺上位クラスタ＝実話者で十分離れており、2 人を融合しない）。
- 残る **B=79%（A↔B 真の混同 ~10%）が下限** — leak 分析と一致。draft 品質として想定どおり。
- anchor の尺しきい値はチューニング要（floor=30–45s で 3、20s で 4、15s で 5）。本番は絶対値でなく**相対（総発話尺の数 % 等）**にすべき。

## Decision

**go。ADR-0004 の sherpa-onnx 路線を継続**（案C の torch pyannote サイドカーには降りない）。
日本語の話者識別は機能しており、ギャップは「過分割」＝後処理問題であって、モデル品質問題ではないため。

- **推奨構成**: segmentation = **reverb-diarization-v1**（9.5MB, MIT ← **誤記。実際は Rev Model Non-Production License。[ADR-0028](./ADR-0028_話者分離segmentationをpyannoteに差し替え.md) で pyannote-segmentation-3.0 に差し替え済み**）、embedding = **TitaNet-large**（101MB, NeMo）、clustering = **threshold（num_clusters=-1, th≈0.80）** ＋ **consolidation（尺 anchor + 最近接 centroid 再割当）**。
- **consolidation は実機検証済み**（上記）: 素の 8–13 ラベルを ~3 へ畳み、purity も上がる。これにより素の過分割は出荷ブロッカーではない。
- **実装形態 = in-process**（公式 `sherpa-onnx` crate を `mojiroku-core` に直接追加）。Rust ビルド・Python 一致・whisper 同居を実機で確認済み（下記）。サイドカー不要。

### このスパイクの限界（誇張しないための注記）

- 正解は**ユーザーの大雑把な手動ラベル**。purity は軟らかい。**厳密 DER は未測定**。
- フレーム整合 77% は **oracle マッピング**（事後に GT 話者→最良クラスタを当てた上限値）。consolidation 前の実 UX は 8–13 ラベルなので、77% は到達可能上限であって出荷品質ではない。
- 音声 1 本のみ。重なり発話（overlap）は未分析。

### Rust 統合スパイク結果（実機）

公式 `sherpa-onnx` 1.13.3 crate（`sherpa-rs` はサードパーティ、公式を採用）を使い捨てクレートで検証:

- ✅ **Apple Silicon でビルド成功**（aarch64-apple-darwin, 14.76s）。`sherpa-onnx-sys` の build.rs が **prebuilt 静的ライブラリ**（`sherpa-onnx-v1.13.3-osx-arm64-static-lib`、libonnxruntime.a 63M ほか）を ureq で DL → 静的リンク。**ソースビルド/cmake 不要**。`static` 既定なので dylib 同梱も不要 → Tauri バンドルが容易。
- ✅ **Python と完全一致**: reverb-seg + TitaNet + th=0.80 で 11 クラスタ・34 セグメント、尺も byte 一致（spk02=270/07=146/12=100…）。**0.43×RT**（Python 0.41×RT と同等）。
- ✅ **whisper 同居は安全**（ADR-0007 の ggml 衝突は起きない）。静的ライブラリのシンボル照合で実証:
  - sherpa は `ggml_*`/`whisper_*` シンボルを **一切定義しない**（onnxruntime ベース）。→ 同名強シンボルの二重定義が原理的に不可能。
  - sherpa(42158) × whisper(1933) の定義済み外部シンボル重複は **186 件で全て libc++ テンプレ実体化の weak（coalesced）**シンボル（`std::__1::regex/string` 系、`___clang_call_terminate`）。libc++/clang ランタイムを除いた**真の強シンボル衝突は 0**。リンカが正規統合する。
  - ∴ **in-process 同居で安全**（llama サイドカー [ADR-0007] と異なり分離不要）。完全な実バイナリ同居実行は Phase 2b 実装時の最終確認とするが、衝突機構が証明的に不在なので低リスク。

## Phase 2b の段取り（go の場合・順序）

1. ~~consolidation スパイク~~ **✅ 検証済み**（上記）。本番実装は「尺 anchor（相対しきい値）＋ turn 単位 TitaNet 埋め込みで最近接 centroid 再割当」。sherpa-onnx は `SpeakerEmbeddingExtractor` で turn 埋め込みを露出する（後処理で実装可、in-process）。
2. ~~Rust 統合スパイク~~ **✅ 検証済み**（上記）。公式 `sherpa-onnx` 1.13.3 crate を `mojiroku-core` に **in-process** で追加（`default-features=false, features=["static"]`）。実装時に whisper+sherpa を載せた実バイナリで 0 セグメント化しないことだけ最終確認。
3. **モデル DL 基盤**: `ensure_model` を reverb-seg(9.5MB) + TitaNet(101MB) に拡張。k2-fsa の release URL（segmentation: `speaker-segmentation-models`、embedding: `speaker-recongition-models`）。
4. **Diarizer 実装 + pipeline 配線（トポロジ注意）**: diarization は **原音声フル解像度に対し、VAD→STT と並列の別ブランチ**で走らせる（whisperX 流）。**VAD の無音除去 PCM を食わせない**こと — さもないと [ADR-0008](./ADR-0008_VADはwhisper内蔵Sileroを独立適用.md) のタイムスタンプ再マップを二重に背負い、無音跨ぎの連結が偽の話者交替を segmentation に与える。マージは STT セグメントと話者 turn の**時間重なり**で `Segment.speaker_id` を割当。永続化往復は装備済み。
5. **file 取込の原本保持**: 現状 mic のみ `recordings/<id>.wav` を残す。後追い diarization のため file 経路でも原本保持が要る。
6. **UI 話者表示**。

## 既知の限界（実装時に対処 or 明記）

- **短時間話者**: consolidation の尺 anchor は「十分喋る話者」でのみ検証済み（102/365/92s）。一言しか喋らない参加者は floor 未満で優勢話者へ吸収されやすい（相対 floor でも救えない）。当面は既知の限界として扱う。
- **速度**: diarization 0.43×RT は whisper STT に**積み増し**（53 分会議で直列 ≈ 40 分+ の計算）。北極星 UX に照らして許容範囲か beta-2 で評価。速度レバーは prebuilt onnxruntime の CoreML EP 同梱可否のみ → 実装時に確認。
  - **実装後のフルスケール実測（2026-06-26, debug, 54分実会議=3215s, node 無し CLI `transcribe_and_diarize_file`）**: 合計 **1722s ≈ 29分**（STT 247s / sherpa diarization 1355s / consolidate 120s）。diarization は **線形確認**（480s→205.7s, 3215s→1355s = 6.7倍入力→6.6倍時間）。0.43×RT は短尺限定でなく**フルスケールでも成立**。実効 ~0.54×RT のバックグラウンド処理として実用範囲。さらなる高速化が必要なら **チャンク分割＋並列 diarization → 埋め込みで跨ぎ結合**（製品判断）。
  - **⚠️「54分で2時間」問題は算法ではなくログ flood**: 実機 `tauri dev` で長尺が2時間級に見えた主因は、whisper.cpp の**逐トークンログ**（54分で 45,863行＝全ログの94%）が node 経由でターミナルへ中継され実行を停滞させていたこと。対策として `stt::WhisperStt::load()` 冒頭で `whisper_rs::install_logging_hooks()` を呼び、ログを破棄（本クレートは whisper-rs を log/tracing feature 無効でリンク。実測: 数千行→10行）。アプリ `transcribe_file` に stage 計時を追加済み。残差（contention/サーマル）はクリーンな実機1回で確定する。

## 出荷前の検証（スコープ外・将来）

推奨構成を**正しくラベル付けされた日本語会議サンプル**で再評価し、信頼できる DER を取る（本スパイクの GT が大雑把なため）。ユーザー提案の据え置き事項。
