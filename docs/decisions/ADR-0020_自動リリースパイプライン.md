# 0020. 自動リリースパイプライン（GitHub Actions・Worker プロキシでマニフェスト動的化・$0 維持）

- ステータス: 採用（**v0.3.0 で稼働実証・2026-06-30**）
- 日付: 2026-06-30
- 関連: [[ADR-0011_配布は未署名dmgでCloudflareとReleases]]（配布の土台）/ [[mojiroku-updater]]（updater 実装）/ [[main-via-PR]]

## Context

アプリ内アップデート（Tauri v2 updater, [[mojiroku-updater]]）は**クライアント側は実装・配線済み**で本番も生きている
（endpoint `mojiroku.com/updater/latest.json`・本物 minisign pubkey・`createUpdaterArtifacts: true`・起動時チェック UI）。
しかし「main 更新→既存ユーザに更新通知」は**成立していなかった**。理由は2つ:

1. **アプリをビルド/署名/公開する CI が無い**（`.github/workflows/` 不在）。リリースは `just build` + `gh release` の完全手動。
2. **updater が見る `latest.json` が静的ハードコードファイル**（`landing/public/updater/latest.json`・version 固定・署名手コピペ）。
   新リリースを Releases に上げても、手で書き換えて Cloudflare に反映しない限りユーザには旧版のまま見える。

[[ADR-0011_配布は未署名dmgでCloudflareとReleases]] は「Metal/whisper.cpp の CI ビルドは不安定」を理由に CI 化を先送りしていた。
本 ADR でその前提を再検証し、CI 化に踏み切る。

## Decision

**version を上げた main マージ（または手動 `workflow_dispatch`）で、ビルド→minisign 署名→署名検証→公開
`mojiroku-releases` への Release 公開→updater マニフェスト更新までを自動化する。**

### 採用構成

- **トリガ**: `push: branches:[main]` ＋ `workflow_dispatch` のみ（`tags:` は付けない＝二重発火/push ループ防止）。
- **2ジョブ**: 無料 `ubuntu` の **gate** が「`tauri.conf.json` の version が `HEAD^` から変化」かつ「releases repo に同 version
  が未在」のときだけ、課金 `macos-26`（Apple Silicon/Metal）の **build-publish** を起動。冪等性は「releases repo に在るか」で担保。
  （ランナーは `macos-26` 必須＝計画時の `macos-14` は macOS 26 SDK 不足で依存 `apple-metal`（`screencapturekit 8.0` 経由）が
  コンパイル不可。実地で判明。下記 Consequences の訂正参照。）
- **ビルド再現性は確認済**: whisper-rs-sys の vendor patch（`[patch.crates-io]` + `vendor/whisper-rs-sys/`・787 files）、
  `.cargo/config.toml` の `MACOSX_DEPLOYMENT_TARGET=11.0`、`src-tauri/build.rs` の clang_rt 動的リンクはすべて commit 済 →
  クリーンチェックアウト＋toolchain だけでビルド可能。モデルは実行時 DL で bundle されないので CI に不要。
- **`tauri-action` は不使用**: 署名は env + `createUpdaterArtifacts` で `npm run tauri build` が行うため不要。
  公開は `gh release create -R daichi8120/mojiroku-releases` で自前制御（安定名リネーム・draft 制御・cross-repo）。
- **クロス repo 公開**: source（private `daichi8120/mojiroku`）→ public `mojiroku-releases`。デフォルト `GITHUB_TOKEN` は
  別 repo に書けないため **fine-grained PAT（`mojiroku-releases` のみに `contents:write`）** を `RELEASES_REPO_TOKEN` で注入。
- **原子的公開**: `--draft` で全3アセット（.dmg / .app.tar.gz / **latest.json**）添付 → 揃ったことを確認 → `--draft=false` に flip。
  draft 中は `releases/latest/download/...` が前リリースに解決し続けるため、途中失敗でもユーザは壊れない。
- **マニフェスト動的化（核心）**: `latest.json` を **Release アセット**として CI が生成・添付し、
  **landing Worker に `/updater/latest.json` プロキシ route を追加**して `releases/latest/download/latest.json` を
  200 で返す（`landing/worker/index.ts`）。静的 `landing/public/updater/latest.json` は撤去。
  → **version 上げ→main マージだけで、焼き付き endpoint の既存 0.2.0+ ユーザに通知が届く**（landing 再デプロイ不要）。
  Worker 変更は一度きりの `npx wrangler deploy`。
- **署名検証ガード**: publish 前に、生成 `.sig` が `tauri.conf.json` の pubkey で `minisign -V` を通ることを確認し、
  失敗ならジョブを落とす。`checkForUpdate()` は全例外を握り潰すため、CI 署名鍵 ≠ baked-in pubkey だと全ユーザが
  **サイレントに**更新失敗する。この検証が「失敗が見える」唯一の場所。

### なぜプロキシ200か（302 ではなく）

updater はマニフェストとダウンロード URL を別々に取得する。プロキシが**本文を 200 で返す**ことでマニフェスト取得に
リダイレクト追従が一切絡まない（更新の確実性が上がる）。ダウンロード脚（`releases/latest/download/...app.tar.gz` →
githubusercontent の 302）は reqwest 既定追従の標準パターン。万一 CDN skew が出ても minisign 署名検証が fail-closed で
誤インストールを防ぎ次回収束。Worker は上流非200で古い200を返さず **503**（= updater 側は「更新なし」扱いで UI を壊さない）。

## Consequences

- **$0 維持は不変**（minisign は Apple codesign と独立・未署名配布のまま動く。Cloudflare secret も不要）。
- **コホート**: v0.1.0 は updater 非搭載→自己更新不可（手動入れ直し）。**0.2.0 以降のみ自動更新対象**。
- **[旧 BLOCKING・解消済み] 非開発機での `.app` 起動**: `src-tauri/build.rs` がユーザ機に無い Xcode toolchain への
  rpath も発行する（`/usr/lib/swift` への rpath は有効）ため、人間の目視を外す自動配布では起動失敗ビルドを撒くリスクだった。
  → **2026-06-30 の 0.2.0→0.3.0 実機 E2E（CI ビルドの .app が clean に更新・起動）で解消**＝CI 成果物が実機で起動することを
  端から端まで実証。
- **[前提の変更] 2026-08-21 に [[ADR-0027_ライセンスをAGPL-3.0とCLAに決定]] で public 化したため、macOS ランナーは無料枠になった。**
  以下は private 時代の記述: private repo の macOS は分課金10倍（1ビルド150–450実効分）。spending limit/有料プラン未設定だと
  ワークフローが起動しない（**$5/Stop usage で設定済み**）。逼迫時は dev の Apple Silicon をセルフホスト runner 化。
- **段階導入（実行済み・2026-06-30 完了）**: いきなり完全自動にせず、①`workflow_dispatch` の dry_run でビルド+署名検証
  （公開しない）→ ②version 0.3.0 で初回リリース公開（latest.json が Release アセットになる）→ ③`releases/latest/download/latest.json`
  が 200 を確認 → ④Worker route を `npx wrangler deploy`・静的 `landing/public/updater/latest.json` 撤去 → ⑤0.2.0→0.3.0 の
  実機 E2E、の順に投入し全段グリーンで成立。
- **実行中に判明した訂正（実地・横展開可）**:
  - **ランナーは `macos-26` 必須**（計画は `macos-14`）。macos-14 は macOS 26 SDK 不足で依存 `apple-metal`（`screencapturekit 8.0`
    経由）の `#available(macOS 26.0,*)`（`MTLSamplerReductionMode` 等）がコンパイル不可。dev 機（macOS 26.5/Xcode 26）と一致させる。
  - **macOS の `base64` は位置引数不可**（`base64 -d <file>` が invalid argument）→ 署名検証は stdin リダイレクト `base64 -d < file`。
  - **Cloudflare Static Assets は dist の一致ファイルを Worker route より優先**（`run_worker_first` 未設定）。当初「Worker route が
    先に評価される」想定は**逆**で、静的 `landing/public/updater/latest.json` を**撤去**して初めて `/updater/latest.json` プロキシが効く
    （撤去前は route がバイパスされ旧版 0.2.0 が固定で返り続けた）。`/oauth/*` は一致アセットが無いので元から Worker が捌けていた。
  - **クロス repo PAT は read だけだと気づけない**: releases repo が public なので `gh release view` は token 無関係に通り、
    `gh release create`（POST）で初めて 403。fine-grained PAT に `mojiroku-releases` の **Contents: Read and write** が要る。
- **残（要ユーザ操作）**: 上記 PAT 書込権限の付与のみ。未付与の間は publish 段が 403 で落ちるが、ビルド成果物を `if: success()` で
  必ず artifact 化してあるため、オーナーの `gh`（releases repo admin）で再ビルド無しに手動公開できる（v0.3.0 はこの手動リカバリで
  公開）。write 付与後は「version 上げ→main マージ」だけで完全自動公開になる。

実装: `.github/workflows/release.yml` / `scripts/make-updater-manifest.sh` / `landing/worker/index.ts`。
運用・Secrets・E2E は [docs/updater-plan.md](../updater-plan.md)。
