# 0024. バックグラウンドジョブ基盤（永続キューでキャプチャと重い処理を分離）

- ステータス: 採用
- 日付: 2026-07-08
- 関連: [[ADR-0021_FFI例外シールドと重処理直列化]]（`HEAVY_ML_JOB` セマフォ＝同時 1 本）/ [[ADR-0023_録音PCMのspool化]]（音声を STT 前にディスクへ確定＝物理分離の土台）/ [[ADR-0017_会議モードのシステム音声キャプチャ]]（per-track が文字起こしの正本）/ [[ADR-0018_話者ライブラリの声紋照合]]（後付け話者分離の声紋引き継ぎ）

## Context

録音 → 文字起こし → 話者分離 → 要約を **同期一気通貫** で処理していた。
`stop_mic_recording` / `stop_meeting_recording` / `transcribe_file` はいずれも録音停止
（またはファイル選択）から STT/話者分離の完了までを 1 コマンド内で待ち、`transcript` を
返していた。このため次のことができなかった:

- **録音後に話者分離だけ後付け**（`diarize_file` は core にあるがコマンド未配線）。
- **音声だけ録って重い処理を後回し**（stop は必ず STT を回す）。
- **文字起こし中に別の会議を録り始める**（処理オーバーレイが画面を塞ぐ・重い処理が UI 経路を占有）。

根っこは共通で、「**キャプチャと重い処理を分離し、音声を正本にジョブ化して後から/並行で
処理・再処理する**」設計に収束する。土台は既に整っていた: spool で音声は STT 前に確定
（物理分離済み・ADR-0023）／core は UI 非依存で疎結合／`summarize` が「後付け処理」の
実証済みテンプレート。欠けていたのは **①ジョブの永続状態 ②既存録音を対象に処理を叩く
コマンド ③再処理する store API** の 3 点だった。

## Decision

**永続ジョブキュー（`jobs` テーブル・v5）＋バックグラウンドワーカーを入れ、キャプチャは
キューの外に置く。** これで後付け話者分離／録音のみ→後処理／並行録音を一気に解禁する。
リアルタイム文字起こしと whisper キャッシュは別フェーズ（今回触らない）。

### 1. 永続ジョブ（スキーマ v5・`store/job.rs`）

`jobs(id, recording_id→CASCADE, kind, status, params, stage, error, created/updated_at)`。
状態機械は pending/running/done/failed/canceled。`params` は enqueue 時にスナップショット
した JSON（言語・話者分離指定）で、**ワーカーは live 設定を読まない**（キュー待機中に設定を
変えても各ジョブは投入時点の指定で走る）。起動時に `requeue_running_jobs` で running→pending
へ戻す（**再起動継続**: 音声はディスクに確定しているので頭から実行し直せば足りる）。
`summaries.stale` は例外的に `ALTER TABLE ADD COLUMN`（非再入・`column_exists` ガード）。

### 2. バックグラウンドワーカー（`src-tauri/src/jobs.rs`）

`JobQueue{ tokio::Notify }` を `app.manage`、enqueue コマンドが `wake()`。ワーカーは
`next_pending_job` → 無ければ `notified().await` で眠る。**ループはジョブの内容では絶対に
死なない**（advisor）: `spawn_blocking` 内の panic（`JoinError`）も core の `Err` も、どちらも
`set_job_failed` に落として次へ進む（JoinError を握り潰さず伝播させるとワーカーごと死んで
以後の全ジョブが pending のまま止まる）。重い区間だけ `HEAVY_ML_JOB` permit を取り
（ADR-0021 流用・同時 1 本＝16GB 機のメモリ枯渇クラッシュ源を作らない）、`kind` で
`run_transcribe`/`run_diarize` に分岐する。

### 3. 非同期フリップ（既存コマンドの破壊的変更・要石で低リスク）

`TranscribeResult.transcript/speakers` はフロント未使用（呼び出し 3 箇所は `recording_id`
だけ使い navigate → DetailView が `getRecording` で読み直す）と調査で確定。よって
stop/transcribe コマンドを **音声を同期で確定 → `insert_recording_only` → enqueue → 即返し**
へ切り替えても呼び出し側はほぼ無変更。順序 `insert_recording_only`（recordings commit）→
`enqueue_job`（FK 参照）→ `wake()` は load-bearing（逆だとワーカーが `not_found` を踏む）。

- `transcribe_file`: **原本コピーを致命化**。フリップ後はワーカーが `recordings/<id>.<ext>` を
  STT 入力に読むため、`copy_recording_original` は best-effort ではなく必須（失敗したら録音行も
  ジョブも作らず `error.recording.copy_failed`。ADR-0023 の rename ゲートと対称）。
- `stop_meeting_recording`: 無音ガード・per-track rename（採用トラックのみ・非採用は削除）・
  再生用結合ミックス生成まで同期。ワーカーは per-track WAV の **存在** で dual/相手のみ/自分のみを
  判定する（非採用削除が判定の前提＝load-bearing）。ミックスは **重い permit を取らない**
  （resample/加算のみ）ので、先行ジョブ実行中でも停止を塞がず新会議を開始できる。

### 4. 進捗イベントの相関付け（最大の落とし穴）

旧 `transcribe://progress` はグローバル（同期 1 本＋オーバーレイ 1 枚だから成立）。キュー＋
複数詳細ビューでは `recording_id` 無しだと別録音の進捗を描く。→ 新チャネル `job://update`
（ライフサイクル遷移も stage 進捗も 1 ペイロード、**`job_id`/`recording_id` 必須**）へ寄せる。
DetailView は `payload.recording_id===id` のみ反映。`summarize://progress` は要約がキュー
対象外なので現状維持。

### 5. 再処理 store API と後付け話者分離

`replace_transcript`（1tx で segments/speakers/duration/rec_fts を差し替え）／
`replace_speaker_assignments`（話者割当更新＋声紋 INSERT OR REPLACE＋speaker_matches 消去＝
再計算＋既存要約を `stale` マーク）。後付け（再）話者分離は **display_name をベスト努力で
引き継ぐ**: `carry_display_names`（L2 正規化済み声紋の cosine 貪欲マッチ・min_cos 未満は
引き継がない・core 純関数）。**会議（Live）は後付け diarize を拒否**する（取得時に相手＝話者分離・
自分＝ソース帰属で確定済み。後から system を再分離して全 transcript に merge すると自分
セグメントが相手話者へ化けて壊れる。コマンド／ワーカー二重で弾く）。

### 6. 録音のみ保存

Home の「音声だけ保存」トグル。ON なら stop/取込は音声を確定するだけで `insert_recording_only`
のみ実行し enqueue/wake をスキップ（`StartJobResult.job_id` は `None`）。後から DetailView の
「文字起こしを実行」（`transcribe_recording`）で処理する。話者分離指定は record 時に確定せず
後の投入時に選び直す。会議はトグル対象外（常に文字起こしまで積む）。

## 検証

- **並行録音（シナリオ⑤）**: 長尺 file を transcribe（running）→ 直ちに会議録音を開始できる
  （キャプチャは permit 不要）→ ライブプレビューが tick を譲りつつ出る → 会議停止で 2 本目が
  pending 直列待ち → 1 本目完了トーストが別画面でも出る。
- **録音のみ→後から文字起こし**: マイク/ファイルを「音声だけ保存」→ 履歴に無 transcript 行
  （0:00/タイトルのみ）→「文字起こしを実行」→ `job://update` 進捗 → transcript/duration 反映。
- **後付け話者分離の display_name 引き継ぎ**: diarize 済み録音で話者改名 → `diarizeRecording` →
  新話者に旧名が cosine マッチで載る/載らない（min_cos 境界）。summaries stale 表示。
- **再起動継続**: transcribe running 中に強制終了 → 再起動 → `requeue_running` で pending 復帰 →
  再実行し完了。
- ビルド/型/テスト: `cargo build/clippy/test`・`npm run build`（tsc+vite）・`vitest` 各グリーン。
- 「動いた」は実音声で確認・品質ゲートは実会議で評価（north-star）。実機 E2E は配布ビルドで実施。

## 影響・制約

- **リリース順序（load-bearing）**: 本体 v5 化で、v4 時にビルドした `mojiroku-mcp` は
  `open_readonly` の未来スキーマ拒否（`version > SCHEMA_VERSION`）で DB を開けなくなる。
  MCP は core を共有し、v5 では `get_recording_detail` が `stale`（`column_exists` ガード）と
  `active_job`（`table_exists` ガード）を読むので **v5 core から再ビルドすれば v5 DB も未 migrate の
  v4 DB も安全に読める**。よって MCP を本体と **同時に再ビルドして出す**（`scripts/build-sidecar.sh`
  が workspace から生成）。MCP 自体のコード変更は不要。
- **`StartJobResult.job_id` は `Option<String>`**（録音のみ保存はジョブ無し＝None）。フロントの
  楽観 seed は `if (res.job_id)` ガード。
- **結合ミックスは同期のまま**なので、長尺会議は停止応答がミックス生成分（数秒）延びる。ミックスを
  ワーカーへ回すと処理中に再生できないため、視聴性を優先して同期に据え置く（STT をブロックしていた
  旧挙動より遥かに速い）。
- **リアルタイム文字起こしは現状維持**（`live_stt` は heavy_job_busy で tick を譲る既存挙動のまま）。
