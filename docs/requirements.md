# mojiroku 要件定義書

> ステータス: ドラフト（初版） / 最終更新: 2026-06-24
> 関連: [仕様書](./spec.md) ・ [アーキテクチャ](./architecture.md) ・ [ADR](./decisions/)

---

## 1. 背景・目的

会議や打ち合わせの**文字起こし → 要約・議事録作成**を、**基本無料**で行えるデスクトップアプリ。

- 既存の文字起こし/議事録 SaaS は従量課金・サブスクが多く、利用が増えるほどコストがかさむ。
- mojiroku は**ローカルモデルで推論を完結**させ、サーバー推論コストを $0 にすることで「基本無料」を成立させる。
- 同時に**ローカル完結＝プライバシー優先**（音声・文字起こしが既定では端末外に出ない）を価値とする。
- 想定アウトカム: 「録音/音声ファイルを入れる → 話者付きの文字起こしと、整った議事録が出てくる」を、追加費用なし・インストール後すぐに体験できる。

## 2. ターゲットユーザー / ペルソナ

- **会議の多い個人・小規模チーム**（PM、リサーチャー、フリーランス、学生など）。
- 議事録作成の手作業負荷を減らしたいが、**月額課金や音声の外部送信には抵抗がある**層。
- 技術リテラシーは中程度を想定。**「インストールしたらすぐ使える（ただ動く）」**ことを重視 → 外部ランタイムの別途インストールは要求しない。

## 3. スコープと段階リリース

ユーザー確定の**最大構成（v1 フルスコープ＝最終形）**は維持しつつ、**実装はリスクの高い順に後置**してフェーズ分割する。スコープ自体を縮小するものではない。

| Phase | 内容 | 特記 |
|---|---|---|
| **Phase 1** | 音声ファイル → 文字起こし → 要約・議事録 | コア価値を最短で提供。**Python ゼロ・torch ゼロ** |
| **Phase 2** | 話者分離（誰が話したか） | sherpa-onnx で実現。品質不足時は案C（薄い Python サイドカー）へ |
| **Phase 3** | マイク録音 | 録音 UI・OS 権限 |
| **Phase 4** | 会議ライブ取り込み（システム音声）＋配布パッケージング | macOS ScreenCaptureKit 等。最難・最後 |

- **In スコープ（v1）**: 上記すべて、ローカル要約＋任意 BYOK、履歴、エクスポート。
- **Out スコープ（v1）**: クラウド同期、チーム共有、リアルタイム字幕、Web 版（→ 将来拡張）。

## 4. 機能要件

| ID | 機能 | 内容 | Phase |
|---|---|---|---|
| FR-1 | 音声入力（ファイル） | mp3 / wav / m4a 等のアップロード | 1 |
| FR-2 | 文字起こし | whisper.cpp（whisper-rs）、日本語 large-v3、Core ML/Metal 高速化 | 1 |
| FR-3 | 要約・議事録生成 | テンプレート（議事録 / 要約 / アクションアイテム抽出）。既定は同梱 GGUF | 1 |
| FR-4 | 編集・エクスポート | 文字起こし/議事録の編集、Markdown / txt / docx 出力、クリップボードコピー | 1 |
| FR-5 | 履歴 | Recording 単位でローカル保存・再閲覧 | 1 |
| FR-6 | 設定 | 要約モデル選択、BYOK キー管理、言語。**既定は同梱モデルで設定不要** | 1 |
| FR-7 | 話者分離 | sherpa-onnx、セグメント単位の話者ラベル、話者名のリネーム | 2 |
| FR-8 | 音声入力（マイク） | その場録音 | 3 |
| FR-9 | 音声入力（ライブ取り込み） | Zoom/Meet 等のシステム音声キャプチャ | 4 |

## 5. 非機能要件

- **性能目安**: Apple Silicon（M 系）で whisper large-v3 を Core ML/Metal により実用速度（実時間の数倍〜十数倍の速さ）で処理。具体数値は spec の宿題として実機計測。
- **プライバシー**: ローカル完結が既定。音声・文字起こしは端末外に出ない。
  - ⚠️ **BYOK（OpenAI/Anthropic 等）を選択した場合は、当該プロバイダにデータが送信される**。「ローカル完結」とのトレードオフを設定 UI で明示する。
- **メモリ予算**: 8GB Mac でも動作すること。STT モデルと要約モデルを**同時常駐させず load/unload**する（spec §6）。
- **総フットプリント / 初回 DL 体験**: whisper large-v3 ≈1〜3GB ＋ 要約 GGUF 数GB ＋ sherpa diarization ≈数百MB。torch を持たないため旧（サイドカー）案より大幅減。合計サイズと初回ダウンロード体験を数値で規定する（spec §10）。
- **動作環境**: macOS を優先ターゲット、次いで Windows / Linux。
- **コスト**: ホスティング $0。ローカル利用は無料、BYOK のみ利用者の API 課金。

## 6. 制約・前提

- モデル DL サイズ（合計 数 GB）。初回起動時のダウンロード体験を設計で吸収する必要がある。
- システム音声キャプチャ（Phase 4）は OS 権限（macOS: 画面収録/オーディオ権限）が必要。
- sherpa-onnx / ONNX Runtime の各 OS 向けバイナリを同梱する必要がある。
- 配布には各 OS のコード署名 / 公証（macOS notarization 等）が必要。

## 7. 既知リスク・トレードオフ（明記必須）

1. **日本語 STT 精度 vs 速度**: small/medium モデルは日本語が弱く、large-v3 は重い。→ whisper.cpp の Core ML/Metal で M 系は実用域に入る。
   - 補足: faster-whisper（基盤 CTranslate2）は **Apple GPU/Metal 非対応**（`device="mps"` 不可、Apple Silicon では CPU 止まり）のため不採用。詳細 [ADR-0005](./decisions/ADR-0005_STTエンジンにwhisper-cppを採用.md)。
2. **パッケージング（旧「最大の脅威」→ 案B でほぼ解消）**: Python / PyInstaller / torch を全廃し、単一 Rust バイナリ＋モデルファイル構成に。残るのは**モデルの DL/同梱と各 OS の署名/公証のみ**。詳細 [ADR-0003](./decisions/ADR-0003_MLをRust単一ランタイムに集約.md)。
3. **チームの Rust 負荷**: 「Rust はシェルだけ」→ ML を含む全バックエンドが Rust に。dev-hub 初の Rust 採用であり、習熟ランプは実コスト。
4. **ML の機動力低下**: モデル差し替え/実験は Python エコシステムより硬い。→ 既定は安定モデルに固定し、実験はオフラインで行う方針。
5. **日本語の話者分離品質が未検証**: diarization は音響ベースで言語非依存寄りだが品質保証はない。→ 早期スパイク推奨。不足時は**案C（薄い Python サイドカーで torch pyannote を Phase 2 遅延起動）**へ降りる。詳細 [ADR-0004](./decisions/ADR-0004_話者分離はsherpa-onnxで実現.md)。
6. **既定 GGUF の日本語議事録品質が体験の下限を決める**: 小型ローカルモデルは当たり外れが大きい。弱いと「無料の議事録ツール」体験そのものが崩れる。→ BYOK を品質パスに位置づけ、既定モデルは早期に実機で品質検証（spec の宿題）。
7. **ライブ取り込みの OS 依存**（Phase 4）と**話者分離の精度限界**。

## 8. 将来拡張

- クラウド同期 / チーム共有、多言語対応、リアルタイム字幕、要約テンプレートのカスタム、Web 版。
- **Rust ネイティブ diarization**（speakrs 等、依存する ort 2.0 が安定したら）への移行で sherpa-onnx を置換し得る。

## 9. 用語集

| 用語 | 説明 |
|---|---|
| STT | Speech-to-Text（音声→文字起こし） |
| 話者分離 / diarization | 「誰がいつ話したか」を区別する処理 |
| whisper.cpp | OpenAI Whisper の C++/ggml 実装。Core ML/Metal 対応 |
| sherpa-onnx | onnxruntime ベースの音声処理ツールキット。話者分離を Python/torch なしで実行 |
| pyannote segmentation-3.0 | pyannote の話者セグメンテーションモデル。本プロジェクトは**その ONNX 重みのみ**を利用（full pyannote.audio パイプラインではない） |
| llama.cpp / GGUF | LLM のローカル推論ランタイムと量子化モデル形式 |
| BYOK | Bring Your Own Key。ユーザーが自分の API キーでクラウド LLM を使う方式 |
| 案B / 案C | B=完全 Rust ネイティブ（採用） / C=話者分離のみ薄い Python サイドカーに降りるフォールバック |
